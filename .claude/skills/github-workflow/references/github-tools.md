# GitHub Tooling: Cloud Sandbox vs. Local

This workflow runs in one of two environments. The procedure is identical in both;
only the commands differ. Figure out which one you are in, then use that column for
every GitHub operation.

## Detect your environment

- **Local** — a `gh` binary is on `PATH` and authenticated (`gh auth status` succeeds).
  Use the `gh` CLI. It infers `owner/repo` from the current checkout.
- **Cloud sandbox** — the remote execution environment (Claude Code on the web,
  GitHub Actions, etc.). **There is no `gh` binary.** Use the GitHub MCP tools
  (`mcp__github__*`). Every call needs `owner` and `repo` passed explicitly (plus
  the issue/PR number where relevant) — nothing is inferred from a checkout.

## Caveats the mapping cannot paper over

1. **PR labels go through the issues API.** `update_pull_request` has **no** labels
   field. A PR is an issue under the hood, so set its labels with `issue_write`
   (`method: update`, `issue_number` = the PR number, `labels: […]`). Same for the
   `help` label during escalation.

2. **No MCP tool deletes a branch.** `merge_pull_request` has no delete-branch
   option and there is no `delete_branch` MCP tool. In the cloud sandbox, rely on
   the repo's "automatically delete head branches" setting, or leave the stale
   branch for later cleanup — do not block a merge on it. Locally, `gh pr merge
   --delete-branch` (and the `gh api -X DELETE …/git/refs/heads/<branch>` verify
   step) still apply.

3. **The comment plus the merge are the approval of record.** The contextless
   reviewer records its verdict by posting the `## PR Review — …` comment (via
   `add_issue_comment` / `post-comment.sh`) and, on a clean review, performing the
   squash-merge. With one account there is no native approve — GitHub refuses a
   review on the author's own PR. When a reviewer account is configured, the native
   review is submitted alongside the comment under that identity (the Native review
   row below; `github-pr-review`'s Native reviews paragraph), and the comment plus the
   merge remain the record either way.

4. **Arbitrary `gh api` calls have no generic MCP equivalent.** Where the local
   flow shells out to `gh api`, find the specific MCP tool for that operation (the
   table above covers the ones this workflow needs). If none exists, treat it as a
   local-only step and note it.

5. **No MCP tool creates or edits a label.** `get_label` only checks whether a
   label exists; there is no cloud tool to create one or change its color.
   Provisioning the canonical label set (github-workflow → "Provisioning the
   labels is a hard gate") is therefore local-only (`gh label create` / `gh label
   edit`) or a human action in the cloud sandbox. If a required label is missing
   or mis-colored and you cannot fix it, stop and ask the user — do not proceed
   with a substitute or no label.

6. **`sub_issue_id` is the issue's internal ID, not its number.** Both
   `sub_issue_write` and the `gh api …/sub_issues` body take the child issue's
   database **`id`** (read it from `issue_read` `get` on the child — the `id`
   field), not its `#number`. Mixing them up links the wrong issue or errors.

### Reading the board: pagination and the cursor-name trap

The board is large enough (400+ items) that every read of it must paginate, and there
are exactly two safe shapes — never a bare, non-paginating call.

**Form 1 — `gh api graphql --paginate`.** `gh` reads the response's
`pageInfo.endCursor` itself and substitutes it into the next request, but only into a
GraphQL variable **named `$endCursor`**. Name the query's own cursor variable anything
else — `$after`, `$cursor`, `$next` — and `gh` has nothing to substitute into, so it
silently re-requests page one forever: no error, no warning, and the first page is
valid, so the loop looks like a slow query right up until it exhausts the account's
shared secondary GraphQL rate limit and starts failing every other agent's concurrent
call too. The variable name is not a style choice; it is the one string `gh`'s
pagination logic matches on.

```
gh api graphql --paginate -f query='
  query($id: ID!, $endCursor: String) {
    node(id: $id) { ... on ProjectV2 { items(first: 100, after: $endCursor) {
      pageInfo { hasNextPage endCursor }
      nodes { id content { ... on Issue { number } } }
    } } }
  }' -f id="$PROJECT_ID" --jq '.data.node.items.nodes[]'
```

**Form 2 — an explicit page loop with a hard cap.** Write the loop yourself, reading
`pageInfo.endCursor` from each page and passing it into the next call under whatever
variable name the query declares, so the naming trap above cannot occur by
construction; guard against a `hasNextPage: true` page with no usable `endCursor`
(`null` or empty) by refusing rather than looping on it. `scripts/lib/project-items-walk.sh`'s `gh_project_items_walk` is this repo's
existing implementation, shared by `board-audit.sh` and `batch-deferred.sh` — reuse it
rather than writing a third copy of the same loop.

**Fetch once per pass, never per item.** Whichever form is used, read the board **once**
into a scratch file at the start of a triage drain or any other pass that touches
several items, and answer every item's board question from that one file — never
re-fetch the whole board per item. Re-fetching per item is the same secondary-limit
failure as the cursor-naming trap, reached from the caller's side instead of the
query's: an orchestrator working a column of a few dozen items this way makes a few
dozen full-board walks where one would do.

## Extraction vs. interpretation

A helper script under `../scripts/` may check a **fact**, never a **claim**. The line
(#732) is between extraction and interpretation, not between prose and non-prose:
`check-manifest.sh` reading a **Log SHA-256** field and recomputing it is prose-adjacent
and completely sound; `check-manifest.sh` reading a **Results** paragraph and deciding
whether it over-claims is not. Write every new check against this boundary.

**Allowed** — a script may:

- read machine data: `gh api` JSON, git plumbing, Project V2 fields, file modes;
- extract a value from an **agreed marker** — a fenced `<!-- evidence {…} -->` footer, a
  `Reviewer-applied:` commit trailer, a `$ <cmd>` / `[exit=N]` log line, a
  `<!-- mirrors: … -->` declaration, a JSONL event key;
- do arithmetic, counting, set comparison, hashing or byte-exact matching on what it
  extracted.

**Not allowed** — a script may not:

- decide whether an English sentence *asserts* something (that a command was run, that a
  log section exists, that a claim is supported);
- guess a language, a file type, or a comment syntax from a name in order to decide what
  a change means;
- treat the presence of ordinary words (`section`, `run`, `raw log`) as a semantic signal.

When a check must choose between guessing and refusing, it refuses (the 2026-09-05 owner
ruling, "minimal heuristics" — issue #732 comment). A refusal costs a review round; a
guess costs a silently wrong verdict, which is worse, because it looks like verification
and is not.

This rule is narrower than, and sits inside, #736's stricter outer boundary: #736 says a
script may not go looking for its own configuration at all (no reading
`work-tracking.md`/`testing.md`/`labels.md` at runtime — that is a **discovery**
question, decided by what the caller passes as an argument). This rule is about what a
script may do with what it is *given*: extract and compare, never interpret. Both rules
stand together; neither supersedes the other's concern.

**The one stated exception (#748): `check-reviewer-commits.sh`'s reads of
`docs/process/testing.md`.** #736's audit classed this script's runtime read of the
no-CI declaration and the agent-instruction exemption paths, both from the tree
**under review at `$HEAD`**, alongside `preflight.sh`'s and `check-manifest.sh`'s
similar-looking fetches of the same file. It is not the same case, and does not move:
the reviewer-applied gate this script mechanises arbitrates conditions a PR's own
author is being judged against, so the source of truth has to be the tree actually
under review, never the caller's belief about it — a caller-supplied value here would
let a PR author configure the very gate that judges their own commits. `preflight.sh`
and `check-manifest.sh` went the other way under #748 (the former drops its
`testing.md` report entirely since nothing downstream consumed it; the latter takes
lint state as a caller-supplied `--lint installed|not-installed|none` argument instead)
because neither decides a gate condition about the tree under review — this one does.
An audit that re-files this read as a #736/#748 violation should stop here first.

## Scripts

The scripts under `../scripts/` are **local-only** — they shell out to `gh api`, and
there is no `gh` binary in the cloud sandbox (see "Detect your environment" above). Each
one documents its own by-hand cloud/MCP equivalent below; run that procedure instead
when reviewing or implementing from the cloud sandbox. The orchestrator role itself is
declared local-only in the platform reference, so this table matters most for a
reviewer or implementer picking up work in the cloud.

**Class** applies the extraction-vs-interpretation rule above to each script, re-verified
against its actual code rather than copied from #732's proposal: `machine` reads only
`gh api`/git/Project-V2 data; `mixed` extracts some things and interprets others (the
interpreting half is named); `machine + 1 heuristic` is otherwise `machine` but carries
one named exception. `stall-check.sh` and `log-consistency-check.sh` read their own
session JSONL (agent-authored, schema'd) and have no cloud/MCP equivalent to map, so they
carry no row in this table. `check-ac-phrases.sh` was retired outright, not narrowed, per
the 2026-09-05 owner ruling on #732 (item 2) — issue #750: it was interpretive on both
ends (it read an issue's AC prose to learn what phrase to look for, then decided whether
that phrase was "present" in another document's prose), produced more residuals than any
other script this milestone (#697, #706, #707, #708, #709, #715), and removing that half
left nothing mechanical behind to keep — the "re-run the resolved grep" step it ended
with has no input once the phrase-and-file extraction that fed it is gone. The owner's
suggested replacement — requiring an AC to name a command a reviewer runs, checkable by
running it rather than by guessing whether two sentences mean the same thing — is left as
an open design question, not decided here; #795 tracks writing it.
`github-workflow/scripts/` has no further scripts.
